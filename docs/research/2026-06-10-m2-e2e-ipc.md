# M2 第 1 步实测：ime-plugin ↔ brain E2E 链路（ipc-v0）

- 日期：2026-06-10
- 结论：**链路打通**。echo 候选 `MOCHI_BRAIN:<input>` 经命名管道进入
  rime_console 候选；降级（kill brain）与恢复（2s 退避重连）行为完全符合
  ipc-v0 规约；延迟余量巨大（插件端到端中位数 0.26-1.3ms，预算 15ms）。

## 链路图

```
按键 → rime_console (simulate key)
        → librime engine → MochiTranslator::Query        [src/ime-plugin]
            → BrainClient::Roundtrip                      15ms 硬超时
                → \\.\pipe\mochi-brain-v0 (消息模式, UTF-8 JSON)
                    → mochi-brain: serve_client 线程       [src/brain]
                        → protocol::handle_message (echo 候选, elapsed_us)
                ← {"v":1,"candidates":[{text:"MOCHI_BRAIN:<input>",...}],"elapsed_us":N}
            → mini_json 解析 → FifoTranslation(SimpleCandidate)
        → 候选/上屏：MOCHI_BRAIN:nihao
```

构建流：`build-steps.cmd` 先把 `src/ime-plugin/` 同步到
`experiments/003-translator-poc/librime/plugins/mochi/`，再走 librime
merged-plugin 构建（静态合并进 rime.dll）。brain 为独立 Rust 进程
（serde/serde_json + windows-sys，选型理由见 Cargo.toml 注释）。

## 实测一：正常链路与延迟（2026-06-10）

命令：起 brain → `rime_console.exe < input`（三行键流
`nihao` / `zhongwenshuru` / `ceshi`，共 23 键 = 23 次 Query）。

stdout（候选上屏，每行一次 commit）：

```
MOCHI_BRAIN:nihao
MOCHI_BRAIN:zhongwenshuru
MOCHI_BRAIN:ceshi
```

stderr 片段（插件侧，每键一行）：

```
[mochi] brain connected
[mochi] Query #1 input='n' seg=[0,1) e2e=10722us brain=up brain_us=13 cands=1
[mochi] Query #2 input='ni' seg=[0,2) e2e=1394us brain=up brain_us=56 cands=1
...
[mochi] Query #23 input='ceshi' seg=[0,5) e2e=1112us brain=up brain_us=8 cands=1
```

### 延迟数据

| 指标 | 样本数 | 中位数 | 最大 |
|---|---|---|---|
| 插件端到端 e2e（run1，含首次部署的冷启动噪声） | 23 键 | 1281 µs | 10722 µs（首键，含建连） |
| 插件端到端 e2e（run2，部署缓存热） | 17 键 | **262 µs** | 1230 µs（重连首键） |
| brain 处理耗时（自报 elapsed_us，两轮） | 23 + 12 键 | **10 / 14 µs** | 56 / 102 µs |

15ms 预算下最坏样本 10.7ms（进程首键，含 CreateFile 建连 + 冷页），稳态
中位数 0.26-1.3ms，**预算余量 >10 倍**。brain 侧 echo 处理 ~10µs，说明
开销几乎全部在管道往返与调度，后续给词图解码留出的 ~5ms 份额无压力。

## 实测二：降级与恢复（kill → 退避 → 重连）

时间线：起 brain → 喂 `nihao`（正常）→ **taskkill brain** → 喂
`duankai`、`haishiduan`（brain 死）→ 5s 后重启 brain → 喂 `huifule`、`zaice`。

stdout：

```
MOCHI_BRAIN:nihao     ← brain 在
duankai               ← brain 死：无候选，librime 提交原始字母（不卡死不崩溃）
haishiduan            ← 仍死：同上
MOCHI_BRAIN:huifule   ← 重启后第一行即恢复
MOCHI_BRAIN:zaice
```

stderr 关键片段：

```
[mochi] Query #5 input='nihao' ... e2e=262us brain=up ... cands=1
[mochi] Query #6 input='d' seg=[0,1) e2e=37us brain=down brain_us=-1 cands=0   ← 断管道当键检出，37µs
[mochi] Query #7 input='du' ... e2e=1us brain=down cands=0                      ← 退避期：瞬时放弃
[mochi] Query #22 input='haishiduan' ... e2e=0us brain=down cands=0
[mochi] brain connected                                                          ← 退避到期后首键自动重连
[mochi] Query #23 input='h' ... e2e=1230us brain=up brain_us=102 cands=1
```

| 验证项 | 结果 |
|---|---|
| kill brain 后继续打字 | ✓ 无候选但不卡死不崩溃（console 正常退出，exit 0） |
| 断连检出成本 | ✓ 首个失败键 37µs（WriteFile 即报 broken pipe），无 15ms 等待 |
| 退避期每键成本 | ✓ 0-1µs（直接短路，不发起连接、不积压请求） |
| 重启 brain 后恢复 | ✓ 2s 退避到期后的第一键自动重连出候选（重连键 1.2ms） |

## 遗留问题

1. **管道名可被抢注**：brain 没用 `FILE_FLAG_FIRST_PIPE_INSTANCE`，第二个
   brain 进程（或任意恶意进程）可在同名管道上再建实例抢接客户端——实测中
   两个 brain 并存时旧实例接走了连接。产品化前要加该标志 + 合适的
   SECURITY_ATTRIBUTES（协议文档无需改，属实现强化）。
2. **brain 不可用时 librime 提交原始字母**：v0 schema 只有 mochi_translator，
   无候选时整行 commit 退化为原始输入。进 Weasel 后应有兜底 translator
   （或保持 composing），属 M2 第 4 步的 schema 设计问题。
3. **commit 通知插件侧未实现**：ipc-v0 的 commit 方向 brain 已实现并单测，
   但插件还没在上屏事件处发送（需要挂 librime 的 commit 通知，与即时学习
   一起做，M2 第 3 步）。
4. **scene/session 为占位值**：插件发的是 `"scene":{},"session":"rime-console"`，
   真实 app/会话身份要等进 Weasel（ADR-004 上下文阶梯）。
5. e2e 首键（建连/冷页）可到 10ms 量级，仍在预算内；若未来贴近预算可在
   translator 构造时预热连接。

## 后记：主会话复测发现并修复一个真 bug（2026-06-10 晚）

1. **GetTickCount64 量化 bug（已修复）**：超时 deadline 原用 GetTickCount64
   计算，其 10-16ms 的更新粒度对 15ms 预算而言一跳就能把剩余等待截成 0ms，
   产生伪超时——复测中两次把健康连接误判为 brain down（2.97ms/4.5ms 即放弃）。
   修复：QPC 微秒时钟 + 等待毫秒数向上取整（brain_client.cc NowUs()）。
   修复后复测 9/9 键零掉线，e2e 中位 1.2ms（机器电源状态影响绝对值，
   预算余量仍 >5 倍）。**教训：贴着毫秒级预算做超时，必须用 QPC。**
2. **librime install 步骤会覆盖 bin 部署数据**：`build.bat librime` 把自带
   示例数据（luna_pinyin/cangjie5 的 default.yaml）拷进 build/bin，悄悄
   替换激活 schema——复测时一度跑的是 luna 而非 mochi（候选出繁体"你好"
   且无 [mochi] 日志即此症状）。每次重建后必须重新部署 rime-data/*.yaml
   并清 bin\build 缓存。
3. **降级/恢复复验**（修复后）：brain 死 → 首键 23µs 检出、后续 0µs 短路、
   console 正常退出；brain 重启 → 冷启动首查询偶超 15ms 触发一次退避（符合
   规约：宁降级不卡键），下一会话完全恢复。
