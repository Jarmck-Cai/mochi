## 一、进程拓扑（2026-06-10 据 librime/weasel 源码调研修正）

```
┌─────────────────────────────────────────────────┐
│ 宿主应用进程（每个应用内）                           │
│   Weasel TSF 客户端（极轻，仅按键转发与上屏）         │
└──────────────┬──────────────────────────────────┘
               │ Weasel 自有 IPC
┌──────────────▼──────────────────────────────────┐
│ WeaselServer.exe（常驻，服务所有应用）               │
│   librime + 我们的 translator 插件 + WeaselUI 候选窗 │
└──────────────┬──────────────────────────────────┘
               │ IPC（命名管道/共享内存，15-20ms 硬超时）
┌──────────────▼──────────────────────────────────┐
│ Brain 服务（常驻本地进程，核心）                     │
│   词图解码器 │ 个人记忆库 │ 小模型(ONNX) │ 策略层    │
│   上下文采集器(UIA) │ 学习循环 │ LLM 调度           │
└──────────────┬──────────────────────────────────┘
               │ 本地调用 / HTTP
┌──────────────▼──────────────────────────────────┐
│ LLM 进程（llama.cpp 本地模型 / 云端 API）           │
│   续写生成 │ 整句重排 │ 新术语挖掘                   │
└─────────────────────────────────────────────────┘
```

源码调研确认的关键事实（详见 docs/research/2026-06-10-librime-translator-feasibility.md）：

- librime 和我们的插件运行在 **WeaselServer.exe 常驻进程**，不注入宿主应用——插件崩溃不带崩宿主（比 v2 初稿预想的好）
- 但 WeaselServer 用全局 `g_api_mutex` **串行处理所有应用的按键**：translator 内阻塞会冻结全系统输入。因此 Brain IPC 必须带 **15-20ms 硬超时**，超时/无 Brain 时降级为纯 RIME
- **Windows 下 librime 运行时外置插件 DLL 未实现**（源码内明文 TODO）：自研 translator 必须静态合并构建进 rime.dll
- 异步续写预览可绕过 librime，直接在同进程的 WeaselUI 层绘制（幽灵文本阶段 1 的实现路径）

Brain 与 LLM 仍为独立进程：智能全部在 Brain，挂掉自动降级；LLM 内存大、生命周期独立、空闲可卸载。

## 二、关键架构决策：filter 还是 translator（ADR-001）

- **方案 A（filter）**：RIME 自带翻译器产出候选，我们只做重排 + 个人词注入。实现快，但天花板低：明月拼音整句转换基线弱于主流商业输入法，且中英混打词图不在我们手里。
- **方案 B（translator）**：接管核心转换——自建词图、自己解码，RIME 只当壳（按键、候选窗、TSF）。
- **建议 B，决定性理由是中英混打**：`ai`/`gan`/`fan`/`sun`/`bang`/`man` 既是合法拼音又是英文单词。"我想用gan"是"敢"还是"GAN"，必须在解码词图内部让拼音弧和英文术语弧用统一打分函数竞争才能做对。filter 架构做不到。

## 三、按键热路径（目标 <30ms，预算 ~25ms）

```
按键 → 词图构建 → 解码 → 个性化打分 → 小模型重排/标注 → 策略层 → 渲染
```

### 1. 词图构建（1-3ms）

对当前键流铺三类弧：
- 拼音音节弧（标准切分 + 模糊音）
- 英文术语弧：个人词库（文档导入 + 行为积累）+ 通用技术词表（~5 万条）+ 任意字母序列兜底弧（允许全新英文词）
- 个人短语弧：记忆库高频整段表达直接成弧

### 2. 解码与打分（2-5ms）

词图上 Viterbi / beam search，线性插值打分：

```
score = λ₁·logP_通用语言模型(KenLM n-gram，大语料)
      + λ₂·logP_个人语言模型(用户 n-gram，时间衰减计数)
      + λ₃·场景先验 P(词 | 前台应用类别)
      + λ₄·上下文匹配（与编辑区光标前文的衔接度）
```

第 0 层记忆库在此起作用：纯查表 + 计数，全内存。用户一次纠正立刻改写 λ₂ 计数——**即时学习的数学实现**，无需训练。

### 3. 小模型（5-15ms，唯一热路径神经网络）

4-6 层、~20M 参数字符级 Transformer encoder，ONNX INT8，三个头：
- **中英意图标注**（序列标注：键流各段是拼音还是英文）→ 修正词图弧先验
- **top-k 路径重排**（输入解码器前 k 条路径 + 记忆库特征）
- **置信度输出**（校准过的，供策略层）

**v0 用 LightGBM 排序器顶替**（特征工程 + <1ms 推理 + 本地秒级训练），先跑通链路再换 Transformer。

### 4. 策略层（<1ms）

根据置信度 + 场景决定 UI 形态：正常候选 / 首选高亮 / 自动上屏 / 幽灵续写。每场景独立阈值，在线统计实际错误率并自适应收紧。

### 延迟预算

| 环节 | 预算 |
|------|------|
| TSF → librime | ~2ms |
| IPC 往返 | <1ms |
| 词图 + 解码 | ~5ms |
| 小模型推理 | ~15ms |
| 策略 + 渲染 | ~2ms |
| **合计** | **~25ms** ✓ |

## 四、异步智能路径（句边界 / 停顿 ≥300ms 触发，预算 500ms）

### 上下文采集（持续后台）

UI Automation TextPattern 读取：焦点编辑控件光标前文（~500 字）、应用进程名、窗口标题；聊天软件尝试读对话区最后几条消息（续写的命门——知道对方问了什么）。

**风险更新（2026-06-10 实测，详见 docs/research/2026-06-10-uia-context-readability.md）：** 微信 4.x（Qt 重写，自带 UIA provider）**完全可读**——对话历史逐条可读、输入框支持 TextPattern、后台亦可读；Chrome/Claude/Discord 编辑区与 caret rect 均 ✓。原"最大不可控风险"初步解除。残余风险：QQ/钉钉/旧版微信 3.x 待补测；Chromium 系窗口最小化时 UIA 树折叠（采集器只能读前台，对输入法场景无影响）；微信消息项无结构化发送者字段，角色归属需启发式。

### LLM 任务

1. **整句重排**：对刚组出的整句 LLM 打分，发现更优转换在候选区温和提示（不回改已上屏内容）
2. **续写生成**：prompt = 编辑区前文 + 对话上下文 + 记忆库检索的用户相似历史表达（**RAG few-shot 注入个人风格，不微调**：即时更新、可解释、无回归风险）→ 双重过滤（LLM logprob + 用户习惯库匹配度）→ 通过才显示幽灵文本。本地 Qwen3-4B 级（有 GPU）或云 API（300-800ms，停顿场景可接受）
3. **新术语挖掘**：空闲扫描近期输入 + 剪贴板，提取候选术语进个人词库（用户可审核）

## 五、幽灵文本渲染：两阶段

- **阶段 1**：续写显示在我们自己的候选窗内（一行灰色预览，Tab 接受）。候选窗是我们画的，零兼容性风险，先验证预测质量
- **阶段 2**：光标锚定悬浮灰字（UIA caret rect / GetGUIThreadInfo 取坐标 + 顶层透明窗 + 匹配宿主字体），按应用白名单逐个攻克（先 VS Code / 浏览器 / Word 等 UIA 友好应用）。跨应用兼容（DPI、深色模式、自绘控件）是长尾泥潭，质量验证通过后再投入

## 六、学习闭环（全本地优先）

```
每次上屏/纠正 → 记忆库计数即时更新（毫秒级生效）
每天空闲时   → LightGBM/小模型本地重训（分钟级）
             → 回归门禁：历史日志回放，top-1 命中率不退步才换模型
每周（可选） → LLM 教练深度分析纠正模式，合成困难样本补充训练集
```

不考虑成本时整个闭环可 100% 本地（有 GPU 时 LLM 也本地），云端教练降级为无 GPU 用户的可选项——隐私问题大幅简化。

## 七、技术选型汇总与风险

| 组件 | 选型 | 状态 |
|------|------|------|
| 输入法壳 | Weasel/librime fork + 自研 translator（静态合并进 rime.dll） | ADR-001（调研已支持 B，待编译实测定案） |
| Brain 服务 | C++ 或 Rust 常驻进程 | ADR-003（未定） |
| 通用语言模型 | KenLM n-gram（大语料）；实验 001 已验证纯 Python trigram 原型 | 成熟方案 |
| 记忆库 | SQLite + 内存缓存，用户可编辑 | 低风险 |
| 小模型 | v0: LightGBM → v1: ~20M Transformer（ONNX INT8） | 低风险 |
| 续写 LLM | llama.cpp 本地（Qwen3-4B 级）或云 API + RAG 个人风格 | 中风险（质量待验证） |
| 上下文采集 | UI Automation | 风险已降级（微信 4.x 实测全可读；QQ/钉钉待补测） |
| 幽灵文本 | 阶段1候选窗内 → 阶段2光标悬浮 | caret rect 已实测可行；阶段 2 高工作量 |
