# ADR-004: 上下文获取改为三级阶梯，UIA 内容读取降级为可选增强

- 状态：Accepted（2026-06-10 用户确认，含三点补充，见"补充决策"）
- 日期：2026-06-10
- 决策者：用户 + Claude

## 背景

v2 设计将"UIA 读取编辑区/对话内容"作为上下文获取的基础手段（DESIGN 第四节）。用户提出两个质疑：
1. 是否只需要知道"是什么场景"，不需要读软件内容？
2. 语料获取：我们本来就是 IME，用户最终选择上屏的内容天然流经我们，何必去外部读？

## 分析

**用户洞察成立的部分：**
- 训练语料的主来源本来就该是 IME 自有输入流（按键、候选选择、纠正、上屏文本）——这是第一方数据，用户使用输入法即同意，无需任何外部读取
- 转换预测（基本盘）需要的"上下文衔接"（打分公式 λ₄），大部分可以用**自有提交流**满足：IME 在每个窗口维护本会话已上屏文本的缓冲，就是现成的"光标前文"近似
- 读屏内容（尤其聊天记录）是全项目隐私最敏感的部分——**对方没有同意被读取**。默认不读内容，商业产品的隐私结构根本性改善

**自有输入流的边界（诚实列出）：**
- 看不到**对方的消息**——聊天场景续写预测的最强条件（"对方问了什么"）只有读屏能给
- 看不到非本会话产生的文本：打开的既有文档、粘贴内容、光标移到文档中间编辑时的前文
- 自建缓冲会漂移（用户移动光标、外部编辑后失真），只能当作近似上下文用于 n-gram 衔接，不能当精确文档状态

## 决策（建议）

上下文获取改为三级阶梯，逐级提升、默认最低级：

```
Tier 0 场景信号（默认，始终开启）
  进程名 + 窗口标题 + 应用类别 → 场景先验 λ₃
  不读取任何内容

Tier 1 自有提交流（默认，始终开启）
  IME 按窗口维护本会话上屏文本缓冲 → 上下文衔接 λ₄ 的近似来源
  同时是训练语料的主来源（第一方数据，含按键/选择/纠正全行为）
  文档导入作为冷启动补充

Tier 2 UIA 内容读取（M5 续写功能的可选增强，按应用 opt-in）
  聊天：读对话区对方消息（续写的命门）
  文档：读光标前既有文本（编辑既有文档时）
  用户明确开启，按应用白名单
```

注：UIA 读取 **caret 屏幕坐标**（幽灵文本阶段 2 的渲染需要）只取坐标不取内容，隐私中性，不受本阶梯限制。

## 补充决策（2026-06-10 用户确认时新增）

1. **冷启动素材完全可选**：用户可提供任何语料（任何语言/格式，实验 001 已验证英文论文也能产出术语词库），也可以什么都不提供——纯靠日常输入流学习。文档导入是加速器，不是前置条件。
2. **场景与语料绑定**：Tier 0 的场景信号同时作为 Tier 1 输入流每条记录的标签。个人记忆**按场景分桶**——用户在微信和写作里的习惯不同（用词、句式、中英比例都不同）。打分时层级回退避免稀疏：场景个人统计 → 全局个人统计 → 通用模型。
3. **Tier 2 定位为备选/补强**：读屏比场景识别复杂得多（隐私 + 逐应用适配两座山），当前专注 M2-M4，Tier 2 推迟到 M5 再评估。

## 后果

- M2-M4 完全不依赖 UIA 内容读取：工程依赖减少，隐私面大幅缩窄
- M5 聊天续写的完整体验仍需 Tier 2（不删除 UIA 路线，实验 002 的结论仍然有效），但变为用户明确授权的增强项
- 自有提交流缓冲需要工程化（按窗口/会话管理、漂移检测、失效策略），成为 Brain 服务的新模块
- 训练语料管线确立为：自有输入流（主）+ 文档导入（冷启动）+ Tier 2 读屏（仅实时条件，不入训练语料）
