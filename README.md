# Mochi — 懂你的个人记忆输入法

> 项目目录：`~/projects/p029-ai-ime/`
> 文档目录：`second-brain/Projects/P029_ai-ime/`
> 启动日期：2026-06-09
> 方案版本：v2（2026-06-10，重构技术分层与产品定义，见文末"方案演进记录"）

---

## 一、项目目标

**让用户觉得输入法懂自己，并且在用户有注意力的地方，明确感知到打字和信息交流变简单了。**

这是唯一的目标。"个人模型""微调""大模型"都只是手段——如果有更便宜的方式实现同样的体验，手段本身没有保留价值。

**灵感来源：** 编程 IDE 中 Copilot 的 Tab 补全。代码有语法和规范，所以容易预测；自然语言打字没有固定规范，**但用户有习惯——习惯就是属于个人的规范**。本项目要回答的问题是：Copilot 式的体验能否迁移到打字？

---

## 二、要解决的痛点（按优先级排序）

中英双语用户（尤其是学术/技术人群）在打字时有高频、持续的摩擦：

1. **中英切换打断思维**（最痛、最高频、竞品最弱）— 写中文时插入英文术语，需要切输入法，思维断裂。**这是第一优先级的单点突破方向。**
2. **输入法不认识"我"** — 通用统计模型，不懂你的专业术语和个人偏好。竞品有词频自适应，我们的差异化在于学得更深（场景、意图、上下文）。
3. **候选词选择消耗注意力** — 每天几百次"从列表里找我要的词"。候选窗口本身就是"强制注意力"的 UI。
4. **同一个拼音，不同场景要不同的结果** — 场景感知是增强项，是手段不是目的。

**核心矛盾：现有输入法理解语言，但不理解用户。**

---

## 三、产品公式：Copilot 四要素的打字翻译

Copilot 的成功 = 强约束（语法降低熵）× 大上下文（看得到整个文件）× 零成本交互（幽灵文本，错了无视）× 收益不对称（对了省一整行）。

逐项翻译到打字场景，得到产品公式：

> **个人记忆** × **当前上下文** × **选择性出手** × **零成本交互**

| 因子 | 含义 | 关键认知 |
|------|------|----------|
| 个人记忆 | 你的习惯、术语、惯用语，即时学习 | 习惯 ≈ 个人的"语法规范"；学的是 P(输出 \| 你的意图, 场景, 习惯) |
| 当前上下文 | 你此刻在回复什么、写什么 | 传统输入法只看到几个拼音，相当于只看当前行的 Copilot——这是它"不懂你"的根因之一，也是最大的技术空白（Windows 上经 UI Automation 读取编辑区/对话上下文） |
| 选择性出手 | 知道什么时候能预测、什么时候闭嘴 | 自然语言的可预测性高度不均匀：模板句、惯用语、高频回复是低熵区段（习惯即规范，接近代码）；新想法是高熵区段，谁也预测不了。**核心能力不是"总能预测"，而是"知道何时能预测"** |
| 零成本交互 | 幽灵文本 + Tab 接受，错误建议如同不存在 | Copilot 的革命一半在交互设计。候选窗口是强制注意力的 UI，幽灵文本是环境式的——这是中文输入法几乎无人认真做过的交互空白 |

**记忆与上下文缺一不可：** 只有记忆没有上下文，是更好的词频统计；只有上下文没有记忆，是通用云输入法做过的事。

## 四、两种颗粒度的预测

| | 转换预测 | 续写预测 |
|---|---|---|
| 定义 | 已打的拼音 → 正确的字词 | 还没打的内容 → 幽灵文本补全 |
| 角色 | **基本盘**，决定用户留不留 | **魔法时刻**，决定用户传不传播 |
| 手段 | 个人记忆 + 上下文，把首选命中率和中英混打做到极致 | 只在低熵区段出现，Tab 接受 |

**依赖关系：续写建立在转换的信任之上。** 首选命中率不行，用户不会信你的续写。基本盘在先，魔法在后，顺序不能反。

### 三个"魔法时刻"

1. **它知道我要打英文** — 打 "wo xiang yong"，候选直接出 "我想用 CNN"，不切输入法
2. **它马上学会了** — 纠正一次，下一次输入就生效（即时学习，不等一周）
3. **它替我把后半句说完** — 在模板句/惯用语处，幽灵文本补全整句，Tab 上屏

## 五、技术架构：按"知识的性质"分层，而不是按"模型的大小"分层

核心认知：**个性化的价值 80% 来自记忆（lookup + 统计），只有 20% 来自泛化；只有泛化才值得用神经网络。** 把"用户打 hfo 时 97% 要 HFO"压进模型权重，是用最贵的方式实现一张查找表。

```
第 0 层：个人记忆库（即时学习，零训练）
  ─ 个人词库 + 选择历史统计，按场景分桶（微信和写作的习惯分开记）
  ─ 用户每次选词/纠正，立刻更新，下一次输入就生效
  ─ 冷启动素材可选：任何语料皆可导入，不提供则纯靠日常输入学习
  ─ 这是"它懂我"的主要来源，成本接近零
  ─ 用户可见、可编辑（信任 + 可解释性）

第 1 层：专用小模型（10-50M 参数，<10ms，每键运行）
  ─ 输入：拼音流 + 个人记忆库特征 + 场景特征 + 编辑区上下文
  ─ 输出：候选排序 + 中英意图标注（序列标注）+ 上屏/续写置信度
  ─ 唯一在按键热路径上的神经网络，专用架构而非通用 LLM
  ─ ONNX 量化后几十 MB，任何机器都能跑

第 2 层：本地/云端 LLM（异步，仅在句子边界或空闲时运行）
  ─ 整句重排、续写预测生成、新术语发现、长上下文意图理解
  ─ 不在按键热路径上，延迟容忍度高（0.5-1.5B 本地或云端均可）

云端教练（每周，角色 = 知识蒸馏，不是权重微调）
  ─ 从打字数据中挖掘新术语 → 生成第 0 层词库条目
  ─ 分析纠正模式 → 生成训练样本，训练第 1 层小模型
  ─ 维护每用户评测集，保证更新不回归
  ─ 只接触脱敏/衍生数据（隐私是商业产品的生死线）
```

### 工程形态

- 基于 **RIME**（中州韵）引擎，Windows（Weasel）优先，自定义 translator/filter 插件
- 模型推理放**独立本地服务进程**，与 RIME 插件经 IPC 通信，不嵌入输入法进程
- 上下文获取：Windows UI Automation API 读取编辑区内容、前台应用、窗口标题
- 推理引擎：ONNX Runtime（第 1 层）；llama.cpp（第 2 层本地 LLM，可选）

### 硬约束（设计红线）

- 用户打字 5-10 键/秒，**每次按键的候选更新必须 <50ms**，热路径上只允许查表 + 小模型
- 学习延迟必须是"即时"——这是留存的来源，任何按周生效的学习机制只能做补充

## 六、关键设计原则

1. **自动上屏的指标不是"平均准确率"，而是"覆盖率下的错误率"。** 错误成本不对称：选错候选损失 1 秒，自动上屏错了损失 5-10 秒外加信任崩塌。目标定义为：**在 X% 覆盖率下错误率 <1%**（校准置信度 + 保守阈值），而不是"准确率 >90%"。
2. **续写预测只在"预测长度 × 置信度"超过阈值时显示。** 短文本读一条错误建议的注意力成本可能比直接打还高——宁可少出手，出手就省一句话。错误建议绝对零干扰：不闪烁、不挤占排版、无需按键取消。
3. **场景不只决定预测什么，还决定敢不敢预测。** 代码错了有编译器兜底；消息是写给人的，措辞代表用户本人。对人交流场景（微信/邮件）的续写阈值必须比文档写作场景（论文/笔记）更保守。
4. **冷启动靠文档导入，不靠行为积累。** 让用户导入自己的论文/笔记/聊天记录，本地提取术语和搭配——第一天就有"它认识 HFO"的体验，不用等三个月。这也是对竞品最直接的差异化。
5. **隐私前置设计。** 全量按键 + 剪贴板对个人工具可接受，对商业产品是致命伤。云端教练只接触脱敏/衍生数据，敏感场景（密码框等）一律不采集。

## 七、核心假设与最便宜的验证

在写任何 RIME 代码之前，先做离线实验验证项目前提：

> **拿自己的历史文本（论文、笔记、聊天记录），离线模拟"个性化排序 vs 通用排序"的首选命中率差异。**

- 若个性化只带来 2-3 个点提升 → 价值假设要重想
- 若带来 10+ 个点（术语密集场景的预期量级）→ 一切投入都值得
- 成本：一两天，不需要输入法框架

## 八、竞争分析与壁垒

### 为什么现有输入法没做这个？
- 搜狗/微软：用户群太大，个性化只能做到词频统计；自动上屏/续写错误的品牌风险高，策略必然保守
- 我们的机会：用户群小而精准（先从自己开始），个性化做到极致，敢做选择性出手

### 我们的壁垒
```
不是小模型本身（开源的）
不是大模型调用（谁都能调）
不是输入法框架（RIME 是开源的）

壁垒 = 个人数据 × 即时学习闭环 × 时间
每个用户的记忆库和小模型越用越独特，别人抄不走
```

## 九、商业模式

- **免费版**：第 0 层 + 第 1 层通用版（个人记忆库 + 小模型），纯本地，成本为 0，本身已有竞争力
- **付费版**：启用云端教练（知识蒸馏 + 个性化小模型训练）+ 第 2 层云端续写，$3-5/月
- **开源策略**：输入法框架 + 本地推理开源；云端教练的数据流水线和蒸馏方法不开源

成本结构较 v1 显著改善：云端不再做每用户 LoRA 微调，教练只做轻量的标注/蒸馏任务。

---

## 十、MVP 路线（按验证顺序，不设时间表）

1. **假设验证**：离线模拟个性化排序收益（见第七节），通过后再投入工程
2. **基本盘**：RIME + 第 0 层记忆库 + 中英混打意图识别——单点把痛点 1 做到极致，对比微软拼音验证
3. **即时学习**：纠正即生效的闭环 + 文档导入冷启动
4. **选择性出手**：置信度校准 → 自动上屏（覆盖率/错误率指标）
5. **魔法时刻**：UIA 上下文获取 + 幽灵文本续写预测
6. **云端教练**：数据脱敏采集 → 蒸馏 → 小模型更新 → 回归评测

## 方案演进记录

- **v1（2026-06-09）**：三层模型架构——云端大模型每周 LoRA 微调 1.5B 本地记忆模型（量化 ~800MB，目标 15-30ms）+ 实时预判层。
- **v2（2026-06-10）**：重构。原因：(a) 1.5B 模型 CPU 上 15-30ms 不现实（实际 50-300ms 量级），且排序/意图判断是分类问题，不需要生成式 LLM；(b) 每周 LoRA 学习个人偏好是"用最贵的方式实现查找表"，学习延迟一周、有灾难性遗忘风险，而即时统计记忆能当场生效；(c) 自动上屏指标从"准确率>90%"改为"覆盖率下错误率<1%"。新增：Copilot 类比推导的产品公式、两种颗粒度预测、幽灵文本交互原语、UIA 上下文获取、文档导入冷启动、隐私前置。
